# Рабочий процесс разработки KTOYA

Версия: 1.0
Дата: 21.08.2026
Статус: действующие правила параллельной разработки.

## 1. Назначение

Этот документ позволяет нескольким чатам/агентам одновременно выполнять крупные задачи KTOYA без создания второго канона и без необходимости пропускать каждое действие через один «управляющий чат».

Канон продукта, технической документации и кода — репозиторий `AinSpiral/Ktoya`. Отдельный чат является временной рабочей средой, а не источником истины.

## 2. Что прочитать перед работой

Перед существенным изменением KTOYA рабочий чат проверяет актуальный `main` и читает минимум:

1. `docs/99-INDEX.md` — навигация и приоритет документов.
2. `docs/02-ROADMAP.md` — текущий этап и границы ближайшей Beta.
3. `docs/03-DECISION_LOG.md` — принятые решения и их причины.
4. профильный документ своей задачи.
5. при изменении фундаментальных принципов — `docs/00-CONSTITUTION.md`.

Если задача использует личные факты, истории, здоровье, карту личности или хронологию Ильи, первичный источник находится в канонической базе Google Drive `02. Личное`; не создавать независимую биографию в репозитории.

## 3. Одна задача — одна рабочая ветка

Существенная задача выполняется в отдельной ветке от свежего `main`.

Рекомендуемый шаблон имени:

`<тип>/<краткая-тема>-YYYY-MM-DD`

Примеры:
- `feat/beta-story-flow-2026-08-22`
- `design/mobile-book-screen-2026-08-22`
- `docs/ai-interview-rules-2026-08-22`
- `fix/privacy-access-2026-08-22`

Не создавать заранее пустые ветки «на будущее». Ветка появляется вместе с реальной задачей.

## 4. Параллельная работа

Разные чаты могут одновременно работать над разными файлами/модулями и не должны ждать друг друга.

Если две задачи затрагивают один и тот же канонический файл или один и тот же участок кода:
- предпочтительно определить один текущий PR владельцем этого участка;
- второй чат либо работает в другом слое, либо после первого слияния заново читает `main` и переносит свои изменения поверх свежей версии;
- нельзя молча перезаписывать более свежие решения другого PR.

Общая структура не использует блокировку всего проекта: конфликт локализуется на конкретных файлах и решениях.

## 5. Pull Request — единица интеграции

Существенная ветка завершается Pull Request в `main`.

До слияния необходимо:
- перечитать изменённые файлы из ветки;
- проверить, что задача соответствует текущему этапу Roadmap;
- запустить доступные тесты/проверки;
- проверить отсутствие случайного удаления и второго канона;
- при конфликте со свежим `main` сначала синхронизировать ветку и повторить проверки.

После слияния именно `main` становится новым каноническим состоянием. Старый чат или его память не имеют приоритета над `main`.

## 6. Когда обновлять документацию вместе с кодом

Не каждый технический коммит требует переписывания всей документации.

В том же PR обновляются только затронутые канонические документы:
- новое подтверждённое продуктовое/архитектурное решение → `03-DECISION_LOG.md`;
- изменение этапности или границ Beta → `02-ROADMAP.md`;
- изменение проверяемых продуктовых требований → `05-PRD.md`;
- новая идея без решения → `04-IDEAS.md`;
- изменение терминов → `06-GLOSSARY.md`;
- значимое фактическое изменение документации → `07-CHANGELOG.md`;
- изменение состава/приоритета документов → `99-INDEX.md`.

Не дублировать одно решение полным текстом в нескольких документах: профильный документ содержит подробность, остальные — статус/ссылку/последствие.

## 7. Границы самостоятельности проектного чата

Проектный чат может без отдельного управляющего чата:
- исследовать варианты;
- проектировать UX и дизайн;
- писать и изменять код;
- добавлять тесты;
- исправлять ошибки;
- создавать необходимые файлы внутри уже принятой архитектуры;
- вести свою ветку и PR;
- обновлять профильную документацию в рамках задачи.

Нужно отдельное решение Ильи, если изменение:
- меняет миссию или фундаментальные принципы;
- существенно меняет продуктовый маршрут или состав первой Beta;
- создаёт новое обязательство по приватности, данным, деньгам или юридическим условиям;
- выбирает долгосрочно значимую техническую архитектуру там, где решение ещё не принято;
- удаляет/ломает ранее подтверждённую пользовательскую возможность вместо обратимого изменения.

## 8. Личные данные и KTOYA

KTOYA может использовать личную Книгу жизни Ильи как первый содержательный пример, но:
- фактическая биография, здоровье, личная хронология и карта личности канонически остаются в Google Drive;
- в GitHub хранится продуктовая модель, схема данных, обезличенные/необходимые примеры и реализация;
- перенос личных данных в тесты/fixtures выполняется только если это действительно нужно и с минимально необходимым объёмом;
- закрытые личные сведения не должны случайно становиться публичным тестовым контентом репозитория.

## 9. Структурный аудит

Отдельный системный аудит следит за структурой Google Drive и межпроектными конфликтами, но не является диспетчером каждого PR и не блокирует разработку.

Для KTOYA аудит проверяет прежде всего:
- не появился ли второй канон на Drive;
- не устарели ли ссылки/навигация;
- не появились ли конкурирующие документы с одинаковой ролью;
- согласованы ли системные статусы Drive с фактическим `main` после значимых этапов.

## 10. Что делать при конфликте решений

Если два чата пришли к разным содержательным решениям:
1. не объединять их молча;
2. определить, какое решение уже подтверждено в каноне;
3. если новое решение меняет подтверждённое — вынести различие, причины и последствия на решение Ильи;
4. после решения обновить один канонический документ и связанные статусы в том же PR.

## 11. Критерий завершения задачи

Задача считается завершённой, когда:
- результат находится в репозитории, а не только в чате;
- изменённые файлы перечитаны;
- проверки/тесты выполнены настолько полно, насколько позволяет текущий этап;
- PR слит либо явно оставлен открытым с понятной причиной;
- `main` после слияния отражает результат;
- при значимом межпроектном изменении системная база Google Drive может восстановить актуальное направление без пересказа старого чата.

## 12. Принцип для активной разработки Beta

Ближайшая цель — не строить всю будущую экосистему сразу, а максимально коротким путём получить качественную первую платную Beta, сохранив точки расширения для следующих этапов.

Новая идея сначала проверяется вопросом: «Нужна ли она текущему этапу?». Если нет — фиксируется в соответствующем будущем этапе/банке идей и не задерживает текущую разработку.
